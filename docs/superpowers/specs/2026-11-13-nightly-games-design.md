# Nightly games: design

Date: 2026-11-13. Builds on `2026-11-12-nightly-design.md` (the "daily games UI" it listed under Next).
Hari asked for both halves ("lets do both") and then said to dive in without more questions. Every
choice below marked **[call]** is the builder's, for Hari to check when he reads this.

## 1. Intent

Add a Games section to `/nightly` with two halves:

1. **Built-in puzzles**: two short, original puzzles each night that train the same skills as the
   brief (numeracy and spotting bad reasoning) and that can be checked right away. An estimation
   puzzle was planned and then dropped, because Hari already plays fermi.gg daily **[call]**.
2. **Your games**: log the scores of the daily games Hari already plays elsewhere (Krillion,
   Chainle, Fermi, Farflung, Hopdown), and see the last two weeks at a glance.

Goals: a quick, satisfying warm-up or cool-down next to the brief, and a record of the habit.

Non-goals:
- hosting or copying any existing game;
- streak rewards or badges;
- anything public (none of this reaches `/notes`);
- pasting share text;
- puzzles tied to tonight's news.

Anti-goals (any of these is a failure even if everything works):
- A puzzle's answer reaches the browser before Hari submits that puzzle.
- A puzzle result changes after it is submitted.
- The Games section breaks or delays the brief flow. It loads and fails on its own.
- Anything here appears on `/notes`, on the homepage, or in public API responses.

## 2. Approaches considered

- **A. Everything model-generated, in the brief call.** One call, ready at 9pm. But it adds risk to
  the brief, which hasn't had a successful live run yet, and a puzzle failure would fail the brief.
- **B. Everything generated by code.** Free and can't fail, but code can't write a convincing
  flawed argument.
- **C. Mixed (chosen) [call].** The code generates the mental-math sprint from the night's date.
  The flaw puzzle comes from one small model call (no web search), made on demand from the Games
  section and separate from the brief. The code chooses the flaw, so the right answer is known by
  construction rather than trusted from the model.

## 3. Constraints

- Vercel Hobby caps a project at 12 functions, so everything goes into `api/nightly.js` as new
  `?action=` values. There is no new function.
- The migration runner keys on the full filename and runs files in sorted order. The shared Neon
  DB already has the pipeline branch's `003_` to `008_` applied, so the new file is
  **`009_nightly_games.sql`** **[call]**. Applying it to the shared DB needs Hari's OK.
- The frontend never imports from `api/`. The game catalog reaches the page through the API
  response.
- Tests run in vitest/node with no jsdom. Logic lives in pure modules that are tested directly, and
  components stay thin.
- Use the light site frame and the existing `nt-*` styles. Mobile first. WCAG AA: labels, live
  regions, keyboard access.

## 4. The night

Everything here belongs to a **night**, using the same `nightDate()` helper: the Eastern date,
running until 3am. Games are keyed by night, not by session **[call]**. That way a game logged at
lunch counts for tonight, even though tonight's brief session doesn't exist until the evening.

## 5. Data (migration `009_nightly_games.sql`)

- `nightly_game_results`, created in 004, is unused, empty and keyed by session. The migration
  first checks that it's empty (a `DO` block that raises if any row exists). Then it drops the
  table and recreates it keyed by night:
  - `nightly_game_results (night date, game text, score numeric NOT NULL, detail jsonb, logged_at
    timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY
    (night, game))`.
  - `game` is either a catalog key (one of Hari's games) or one of `puzzle_sprint`, `puzzle_flaw`.
- A trigger rejects any UPDATE of a row whose `game` starts with `puzzle_`, because puzzle results
  are final. The app can update Hari's own game rows (to correct them) until the night closes.
- `nightly_puzzles (night date PRIMARY KEY, flaw jsonb NOT NULL, created_at timestamptz NOT NULL
  DEFAULT now())`. Rows are inserted with `ON CONFLICT (night) DO NOTHING` and then re-read, so if
  two generations overlap, the first one is kept.
- Read `date` columns as `date::text` (as in 004), and `numeric` as `::float8`.
- A text test for the migration, like `api/_lib/nightlyMigration.test.js`.

## 6. The puzzles

### Sprint (code, no model)
- Five problems, generated by an RNG seeded with the night date, so the server can regenerate them
  to score them. The kinds are consulting-flavoured, with round inputs **[call]**:
  - percent of a number;
  - percent change;
  - price times volume;
  - a per-unit division;
  - break-even units, fixed cost / (price - variable cost).
  Answers are exact integers or have one decimal place.
- An answer counts if it is within 1% of the true value **[call]**. A blank answer counts as wrong.
  The score is the number correct (0-5), and `detail = { seconds, correct: [bool x5], answers }`.
- The page shows a Start button. The problems appear when Hari presses Start, and the time runs
  from Start to Submit. The page measures it and sends it as `seconds`, capped at 3600. Hari gets
  one attempt.

### Spot the flaw (the code picks the flaw, the model writes the argument)
- The code holds a fixed list of ten flaws, each with a name and a one-line definition:
  - survivorship bias;
  - base-rate neglect;
  - correlation taken as causation;
  - selection bias;
  - small sample;
  - regression to the mean;
  - sunk cost;
  - percent vs percentage points;
  - cherry-picked time window;
  - Goodhart's law.
- The code picks the target flaw (no repeat within the last 7 nights where the data allows) and a
  setting (an industry or business function). It then picks three distractors from the rest and
  shuffles the four choices.
- The model writes an argument of 3-5 sentences, set in that setting, whose central inference
  commits exactly that flaw without naming it. It also writes a 2-sentence explanation of where
  the flaw is.
- Hari picks one of the four. The score is 1 or 0. After he submits, the page reveals the right
  answer and the explanation.

### Model call
- One structured-output call (`output_config.format`, effort `low`). It uses the existing `MODEL`
  and the existing `send`, deadline and refusal handling. It returns `{ argument, explanation }`,
  which is validated with zod. If the output is invalid and time allows, it retries once.
- The stored puzzle is `{ flaw_key, setting, argument, choices: [4 names], answer_index,
  explanation }`.
- The system prompt follows the house rules: the argument is original, names no real people or
  companies, and doesn't use current news.

## 7. Your games

- A catalog lives in `api/_lib/nightly/games.js`. Scoring was read from each game's own site on
  2026-11-13 (Krillion's came from a third-party guide). Each entry is
  `{ key, name, unit, min, max, decimals, lowerIsBetter, url }`, and no key starts with `puzzle_`.

  | key | name | unit | min | max | decimals | better | url |
  |---|---|---|---|---|---|---|---|
  | krillion | Krillion | points | 0 | 700 | 0 | higher | https://krillion.io |
  | chainle | Chainle | points | 0 | 5000 | 0 | higher | https://chainle.io |
  | fermi | Fermi | × off | 1 | 1000 | 2 | lower | https://fermi.gg |
  | farflung | Farflung | km | 0 | 100000 | 0 | higher | https://farflung.game |
  | hopdown | Hopdown | metres | 0 | 100000 | 0 | higher | https://hopdown.io |

  - Neither Farflung nor Hopdown publishes a maximum, so their 100,000 is a guard against typos
    **[call]**.
  - Fermi's score is its daily average multiple, where 1× is perfect. Its cap of 1000 is also a
    guard **[call]**.
  - Hari edits this list as his games change.
- Logging a score is an upsert for tonight. Hari can correct it until the night closes, and there's
  no delete **[call]**.

## 8. API (all in `api/nightly.js`, all `auth: true`)

- **`games`** (GET) returns the games payload described below.
- **`puzzles`** (POST) generates tonight's flaw puzzle if it's missing, then returns the payload.
  - `MODEL_NOT_CONFIGURED` → 500.
  - `PUZZLES_FAILED` → 502, with `details.reason` set to the ModelError code.
- **`solve`** (POST) takes `{ night, puzzle: 'sprint'|'flaw', answer }`, with a zod schema per
  kind:
  - sprint: `{ answers: (number|null)[5], seconds }`;
  - flaw: `{ choice: 0..3 }`.
  The server scores it and stores it insert-only, then returns the payload. Errors, all 409:
  - `NIGHT_CLOSED` when `night` isn't tonight;
  - `ALREADY_SOLVED`;
  - `NO_PUZZLES` when the flaw puzzle doesn't exist yet.
- **`log`** (POST) takes `{ night, game, score }`. It's checked against the catalog: a known key, a
  number within min..max, and at most `decimals` decimal places. If `night` isn't tonight it
  returns 409 `NIGHT_CLOSED`. Otherwise it upserts the score and returns the payload.
- **Payload**, built from an explicit allow-list like `sessionView`:
  ```
  { night,
    catalog: [{ key, name, unit, min, max, decimals, lowerIsBetter, url }],
    puzzles: {
      sprint: { problems: [{ prompt }], result: null | { score, seconds, correct, answers: [num] } },
      flaw:   null | { setting, argument, choices,
                       result: null | { score, choice, answerIndex, flawName, explanation } } },
    logged: { [gameKey]: score },                // tonight
    history: [{ night, game, score }] }          // the last 14 nights, puzzles included
  ```
  An unsolved puzzle never includes `answer_index`, `explanation` or the sprint answers. A test
  checks this, like the existing no-early-leak test.

## 9. The page

A **Games** section goes below the existing body of `/nightly` and renders in every view
**[call]**. It has its own fetch and its own loading, empty and error states, so a failure there
never touches the brief.

```
Games
  Puzzles                                     (two cards)
  [Sprint]  5 quick calcs · Start → inputs → Submit → "4/5 in 52s" + which were wrong
  [Flaw]    argument · 4 radio choices · Submit → right/wrong + the flaw's name + explanation
            (if not made yet: "Make tonight's flaw" button, then "Making…")
  Your games                                  (each name links to the game)
  Krillion [ 540 ] Chainle [ 4210 ] Fermi [ 1.94 ] Farflung [ 8200 ] Hopdown [ 3100 ]  Save
  Last 14 nights   table: rows = games and puzzles, columns = nights, cells = score or ·
```

- Components go in `src/private/nightly/games/`. The pure logic goes in tested `.js` modules: view
  state, payload helpers, score formatting and the history grid. Calls go through the existing
  `request` helper.
- A 401 sends Hari to `/login`, like the rest of the page.
- Accessibility:
  - every input has a label;
  - one live region announces results;
  - the history is a real `<table>` with headers, and it scrolls sideways on a phone.
  - Game links open in a new tab with `rel="noopener noreferrer"`.

## 10. Testing

- **Sprint generator:** the same night always gives the same problems, and different nights give
  different ones. All five kinds appear, answers stay in range, and the 1% tolerance holds.
- **Flaw choices:** the shuffle includes the target exactly once among four distinct choices, and
  the picker never repeats a flaw used in the last 7 nights.
- **Payload allow-list:** no answer fields before a puzzle is solved, and present after.
- **Handler:**
  - auth on all four actions, 405s and zod 400s;
  - `NIGHT_CLOSED`, `ALREADY_SOLVED` and `NO_PUZZLES`;
  - log range and decimal checks: Fermi 1.94 is accepted, Krillion 540.5 is rejected;
  - a failed puzzle generation leaves nothing stored.
- **Model request:** the puzzles request has no tools and uses a strict schema, and its output is
  validated.
- **Other:** the migration text test, and the function count stays at 10.
- **Quality gate:** the full vitest suite and the production build. The project has no eslint.
